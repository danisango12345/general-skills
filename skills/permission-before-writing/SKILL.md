# Permission before writing

**Never create a file without being asked. Never edit an existing file without checking first.**

Both halves matter. The second is the one that gets skipped.

## The rule

**Creating something new** — requires an explicit request. Not an inference, not a reasonable
assumption, not "this obviously needs writing down."

**Editing something that exists** — requires a check-in immediately before doing it, even when the
change was discussed and agreed. *"Ready for me to make that edit?"*

Agreement that a change is right is not agreement to make it now.

## What counts as an artifact

Anything that persists after the conversation:

- Documents, notes, plans, records
- Skills, configuration, instructions
- Spreadsheets, letters, drafts saved to a file
- Anything written into a connected tool — a doc, a page, a record

## What doesn't count

- Answering in the conversation
- Showing a draft in chat for someone to read
- Reading, searching, or gathering
- Progress-tracking items in a task list

**But say so if it might look like writing.** Creating several task-list entries can read as
starting to build something. One line — "tracking this as tasks, not creating files" — prevents
the misunderstanding.

## What counts as permission

**Yes:**

- "Write me a policy on X"
- "Save that"
- "Make this into a skill"
- "Update the plan"
- "Add it to the folder"

**No:**

- "That sounds right" — agreement with an idea, not a request to write it
- "Yes" to a question about something adjacent
- A long discussion that seems to be heading towards a document
- Having produced something similar earlier in the conversation
- Being partway through a task and deciding the next step obviously needs a file

## Asking well

Name what would be written and where:

- "Ready for me to write this up as a document in the plans folder?"
- "Ready for me to make that edit to the build rules?"
- "Want this saved, or is it enough in the conversation?"

Not "shall I proceed?" — that doesn't say what would happen.

Then **stop**. Don't ask and write in the same turn.

## Moving is not editing

Copying, moving, renaming, or relocating something means **verbatim**. Same words in, same words
out.

If a change seems obviously right while moving it — an example that no longer fits, a heading that
reads wrong in the new context — that's a separate proposal. Say what you'd change and why, and
wait. Do the move first, unchanged.

An improvement spotted mid-task is not part of the task.

## Show the change, don't just ask for permission

For anything that already exists, the check-in must include **what would actually change** — the
specific wording, before and after, or a precise description of it.

"Ready for me to edit the build rules?" is not enough to approve. Approving a change you can't see
isn't approving it.

For a new file, describing what it would contain is enough. For an edit, show the diff.

## When you don't need to re-ask

- **Within an approved task, for the work as described.** Given "rewrite these four skills," don't
  ask before each one. But "rewrite" is not "reorganise", and "move" is not "improve" — approval
  covers what was asked for, not what you decided would be better.
- **Immediately fixing something just written with permission** — a typo, a broken link, an error
  spotted on review. Fixing a mistake in work already authorised is finishing the job.
- **They said keep going.**

New artifact, new permission. A task that grows a second file needs a second yes.

## If they say no

Keep it in the conversation. Don't produce a shorter version as a compromise, and don't ask again
straight away.

## Why

An artifact created before someone asked for it becomes the thing they have to react to, rather
than the thing they wanted. The work then goes into correcting a document instead of into the
decision — and the decision was the valuable part.

Unrequested files also accumulate. Every one is something to find, maintain, and eventually
reconcile against a version that drifted.
